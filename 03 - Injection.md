# Внедрение кода (Injection)

### Цель работы

Выявить наличие уязвимостей внедрения кода в веб-приложении, проанализировать возможность выполнения несанкционированных запросов к базе данных или исполнения произвольного кода на стороне сервера. 

## Ход выполнения

### 1) Разведка

Для анализа был выбран модуль SQL Injection в DVWA. Был перехвачен типичный запрос при вводе ID=1:

<img width="570" height="250" alt="изображение" src="https://github.com/user-attachments/assets/6028d97d-982a-43ba-a2d0-39d79102a83d" />

Данный модуль принимает идентификатор пользователя (User ID) через GET-параметр и возвращает соответствующую информацию из базы данных. В ответ же сервер вернул информацию о пользователе с ID=1:

<img width="315" height="140" alt="изображение" src="https://github.com/user-attachments/assets/000bd8e7-a611-45b4-acec-31cffaf71767" />


Для успешного извлечения данных необходимо узнать, сколько столбцов возвращает исходный запрос. Для этого использовал команду:

```sql
1' ORDER BY 2-- 
```
<img width="330" height="135" alt="изображение" src="https://github.com/user-attachments/assets/a7443c02-b427-4d6a-9d6a-a1f2729b4293" />

Запрос выполнился успешно. Но уже при попытке сортировки по третьему столбцу появилась ошибка, что указывает на использование в запросе только двух столбцов:

<img width="692" height="87" alt="изображение" src="https://github.com/user-attachments/assets/d2ca2a88-7297-4580-bb04-d9e137e13efd" />

Для понимания того, какие столбцы отображаются на странице, был введен UNION-запрос:

```sql
1' UNION SELECT 1,2-- 
```

<img width="311" height="190" alt="изображение" src="https://github.com/user-attachments/assets/b3a37a32-88d6-40a4-bfaa-591a6a69568a" />

Цифры "1" и "2" отобразились на месте имени и фамилии. Значит обе позиции можно использовать для вывода данных.

### 2) Атака

Для получения списка всех таблиц в текущей базе данных был использован запрос, обращающийся к системной таблице `information_schema`, которая хранит метаданные о всех объектах базы данных:

```sql
1' UNION SELECT 1,group_concat(table_name) FROM information_schema.tables WHERE table_schema=database()-- 
```

<img width="680" height="194" alt="изображение" src="https://github.com/user-attachments/assets/fdf117b8-2968-4fb6-9814-6a4d2ca2c50f" />

В ответе отобразились таблицы: **guestbook, users**. Таблица **users** представляет наибольший интерес, так как предположительно содержит учетные данные пользователей.

Для извлечения данных из таблицы users необходимо сначала узнать названия ее столбцов. Был использован запрос к information_schema.columns:

```sql
1' UNION SELECT 1,group_concat(column_name) FROM information_schema.columns WHERE table_name='users'-- 
```

<img width="679" height="194" alt="изображение" src="https://github.com/user-attachments/assets/aaa6723c-c22a-46f9-a651-56b512e75a1f" />

В ответе получены названия столбцов: **user_id, first_name, last_name, user, password, avatar, last_login, failed_login**. Наибольший интерес представляют столбцы **user** и **password**.

### 3) Эксплуатация

Зная названия интересующих столбцов, был составлен финальный запрос для извлечения учетных данных всех пользователей системы:

```sql
1' UNION SELECT user,password FROM users-- 
```

<img width="410" height="420" alt="изображение" src="https://github.com/user-attachments/assets/0b592634-ff65-452e-8831-382393cefc8a" />

Полученные хеши паролей можно попытаться расшифровать. Например, для логина **1337** хеш `8d3533d75ae2c3966d7e0d4fcc69216b` соответствует паролю **charley**:

## Выводы о защищенности

В результате анализа выявлена SQL-инъекция, позволяющая несанкционированно извлекать данные из базы. Отсутствие фильтрации входных данных в параметре `id` дает возможность модифицировать структуру SQL-запроса, что привело к получению учетных данных всех пользователей и успешный вход в систему. Эта возможность подтверждает критичность уязвимости.

Данная атака классифицируется как:
- **CWE-89: Improper Neutralization of Special Elements used in an SQL Command** - SQL-Injection.
